## 生成正确性

CLI 的 `--target aarch64` 会选择 AArch64 条件分支，不再默认安装 x86-64 架构宏。x86_64、win64、wasm32 分别使用对应的宏集合。`#ifdef`、`defined` 和直接读取宏的 `#if` 应一致。

保持 1.0 的公共结构和函数签名。`@cli.platform_for` 描述整数数据模型；直接使用解析库的调用者需要同时指定架构宏：

```moonbit
let options = @cparse.LoadOptions::new()
let arm_options = {
  ..options,
  platform: @cli.platform_for(@layout.Target::aapcs64()),
  defines: ["__aarch64__=1"],
}
```

生成或比较含非法整数常量表达式的头文件会产生诊断，避免把错误结果用于枚举、数组或位域布局。严格模式拒绝尾部未消费 token、已求值分支中的除零/模零及不支持的移位。未选中的分支仍检查语法，`0 && (1/0)`、`1 || (1/0)` 等合法短路条件不会误报。

三元表达式的有无符号属性由两个操作数共同决定。此维护不声称实现完整的 C 编译器语义；发现不支持的表达式应明确诊断，不以猜测结果代替验证。

## Windows 启动

MSVC 环境捕获使用 `cmd /u` 的 UTF-16LE 输出，不依赖 Python 的默认本地编码。无需先设置 `PYTHONUTF8=1`。探测仍需要 Visual Studio Build Tools、Windows SDK 和现有项目配置。

修复对普通 Python 启动和 UTF-8 模式均有检查。环境变量输出不写入诊断日志。编译器配置失败时按提示使用 Visual Studio developer prompt 排查。

## 自动化验收

```sh
moon update
moon check --target wasm-gc
moon test --target wasm-gc
moon info
python scripts/check-api.py
moon fmt --check
python scripts/verify-parser-corpus.py
python -X utf8=0 scripts/verify-v11.py --native
```

1.1 专项检查需要 clang，执行四个目标的宏选择对照、表达式拒绝/分支结果对照、Windows 环境解码单元检查，以及真实模板的 doctor/validate。证据写入 `_build/v11-*/summary.json`。原有 0.8、0.9 与 1.0 原生验收继续保留在 CI。
